### Verification and Learning

- 최종 검토 후속 변경 범위: 활성 계획 2곳의 명칭, 프록시 안내의 줄 번호와 갱신일, 트랜잭션 안내의 갱신일, Issue 목차와 이 기록 및 체크포인트. 제품 소스, 실행 설정, 의존성과 DB 변경 없음
- 재검증: 계획은 두 명칭만, 프록시 안내는 줄 번호 제거와 갱신일만, 트랜잭션 안내는 갱신일만 변경했는지 원문 대조. Markdown 구조와 변경한 표 정렬, 로컬 링크 및 앵커와 승인 조건 확인
- 이전 통과 근거: 이 기록의 Verification에 보존한 단위 179개, PostgreSQL 통합 148개, 별칭 자동화 41개와 인증 E2E 84개 및 포맷, lint, 타입 검사, 빌드와 Docker 검증 유지. 이번 문서 전용 변경에서는 제품 검사를 재실행하지 않았음
- `ce-compound` 판단: 단순 명칭 누락은 수정 diff로 이유를 알 수 있고 프록시 신뢰 경계 등 제품 학습은 기존 solutions에 있어 새 문서 생략. 임시 검토 실행기의 예약 보호와 UTF-8 처리 근거는 로컬 검토 자료에 보존. 프로젝트 제품 규칙으로 추가하지 않음
- 용어 기록: 새로운 도메인 용어 없음. 별도 용어집 생성 없음

### Accepted Limits and Delivery Checks

- 토큰 최소 권한: 팀 전체 권한의 VERCEL_TOKEN이 유출되면 별칭 갱신 외의 리소스에도 영향 가능. 게시 전에 Vercel이 허용하는 가장 좁은 권한인지 확인 필요. 검토자는 실제 토큰 범위를 확인하지 않았으며 비밀값을 출력하거나 기록하지 않음
- Preview 자동화: 최종 게시 HEAD의 원격 CI, 최초 실제 READY 이벤트의 repository_dispatch 실행, Vercel 토큰의 실제 실행 권한과 고정 별칭 대상을 게시 후 확인 필요. queue 키의 공식 지원 확인은 실제 자동 실행 성공을 뜻하지 않음
- 배포 경쟁: 마지막 PR 재확인과 별칭 쓰기 사이 force-push가 발생하면 잠시 이전 HEAD를 가리킬 수 있음. 새 READY 실행이 완료된 경우에만 교정 가능. 현재 HEAD 확인과 게시 후 수동 대조를 유지하며 이번 명칭 변경에서 공급자 간 원자성은 추가하지 않음
- 공급자 오류: 현재 별칭의 대상 배포가 삭제돼 404이면 수동 복구 필요. 일시적 5xx 자동 재시도는 없으며 실패 확인 후 재실행이나 후속 READY 확인 필요. 성공으로 처리하지 않는 경계는 유지
- ngrok 운영: edge에서 Preview 쿠키와 공유 비밀값을 처리하므로 운영용과 분리한 Preview 전용 값 필요. 서명된 주소 없는 직접 요청은 한도 버킷 공유. 터널 자동 재시작은 없으며 PC와 Docker 및 네트워크 유지 필요. 이전 실제 연결 검증은 [Frontend 기록](01-frontend.md)에 보존
- 테스트 한계: repository, repositoryId, projectId, teamId와 문자열이 아닌 git.ref 거부를 각각 검증하는 사례 및 별칭 POST 실패를 직접 검증하는 사례는 미추가. 기존 41개 검사로 확인한 경계를 유지하며 보고된 재현 결함이 없어 이번 문서 수정에서 확장하지 않음
- Workflow schema 전용 검사 도구 미실행. queue 조합은 공식 문서와 원문 대조로 확인했으며 최종 실제 Actions 결과 확인은 남은 전달 조건으로 유지
- DB 이전: Claude는 migrator 내부 구현이나 실제 DB를 다시 검사하지 않았음. migration 파일 23개 원문 유지와 기존 빈 DB 및 재적용, schema와 Docker 검증을 근거로 유지
