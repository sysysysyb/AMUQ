#### U2. Signup API and Email Delivery

- **Codex**: 이메일 → 인증번호 → 비밀번호 설정 순서로 전환했음. 남이 먼저 등록한 비밀번호가 이메일 소유자의 인증만으로 활성화되던 기존 가입 경로 차단
  - **가입 완료:** [completeSignup](../../apps/backend/src/modules/auth/service.ts)에서 서버가 인증된 이메일을 선택하도록 구현했음. 계정 생성과 인증 토큰 사용 처리를 함께 저장하고, 중간 실패 시 모두 취소하도록 처리했음
  - **기존 계정 보호:** 활성 계정의 비밀번호는 덮어쓰지 않도록 유지했음. Google 전용 계정에 비밀번호를 추가할 때도 Google 추가 인증을 요구하도록 구현했음
  - **미인증 계정 처리:** 옛 가입 방식으로 이메일을 선점한 계정은 실제 소유자의 인증 후 기존 사용자 ID를 유지하며 가입을 마치도록 구현했음. 선점자가 정한 옛 비밀번호, 토큰, 세션은 폐기했음
  - **구 가입 종료:** 이전 가입, 메일 인증 API는 `410 signup_flow_retired`를 반환하고, 옛 인증 링크는 새 가입 화면으로 안내하도록 변경했음. 기존 비밀번호 재설정은 유지
  - **메일 속도:** worker가 새 발송 대기를 2초마다 확인하도록 변경했음. 대기 작업은 중복 추가하지 않고, 기존 1분 재시도와 메일 내용, 중복 발송 방지 키 유지
  - **정리 주기:** 만료 자료 정리는 1분에 최대 한 번으로 제한했음. 실제 실행은 1~2분 간격이 될 수 있음
- **Claude review**: 최초 P2 4건, P3 6건과 후속 소스, 문서 보완 사항 제시
- **Codex response to review**: 같은 인증 토큰으로 몰리는 비밀번호 해시 계산, 기기 시계 오차, 삭제된 가입 시도의 재시도 수정. 번호 재전송 제한과 가입 완료 제한이 서로의 버튼을 막던 문제도 수정했음
- **Claude re-review**: 소스 수정과 문서 정정의 처리 이유 확인했음. 이전 운영 계정이 없다는 사용자 확인에 따라 옛 Google, 미인증 비밀번호 혼합 계정의 호환 처리를 범위에서 제외했음
- **검증:** 합동 U2에서 가입 완료 7개, HTTP 2개, 화면 5개의 실패를 먼저 확인한 뒤 구현했음. 동시 가입, DB 실패 시 취소, 요청 재시도, 시간 차이, 429 안내도 검사했음. 서버와 화면을 합친 당시 결과는 아래 검증 표에 기재했음
  - **실제 확인:** 사용자가 메일 수신, 가입, 로그인과 빨라진 메일 도착 확인했음. Google 로그인, 계정 연결은 이후 Docker preview에서 확인했음
  - **비용 확인:** 2초 조회는 worker당 하루 최대 43,200회임. 로컬 DB 100회 조회에서 평균 약 0.68ms, 95백분위 약 0.84ms 확인했음. 운영 부하, 청구액은 측정하지 않음
- **남은 한계:** 이메일을 다시 인증해도 서버가 이미 안내한 가입 재시도 시각까지 대기하도록 유지했음. 서명 키를 삭제하는 것만으로 이미 발급한 인증 완료 토큰이 즉시 취소되지는 않음

### EXTRA-04. Reject Blank Google Email

- **Codex**: U02의 Google 신원 검증에서 이메일 공백 제거 후 빈 값을 거부하도록 수정했음. 이전에는 원문이 비어 있는지만 검사하고 반환할 때 공백을 제거해, 공백만 있는 이메일이 빈 문자열로 통과했음

#### Codex

- **Origin 검사 순서:** `routes.ts::registerAuthRoutes`에서 허용 출처 검사를 로그인 IP 예산 차감보다 먼저 수행하도록 옮겼음. 로그인과 비밀번호 계정 연결 모두 누락된 출처, `null`, 허용되지 않은 주소를 403으로 거부하고 DB에 접근하지 않음. 허용된 출처의 기존 로그인 제한은 유지함.
- **test 주소 허용:** `environment.ts::authApiConfig`는 development와 test에서 선택적으로 지정한 API_ORIGIN을 검증 후 허용함. HTTP 또는 HTTPS 주소만 받고 경로와 인증 정보가 있는 주소는 거부함. production에서 API_ORIGIN을 거부하는 조건은 유지함.
- **실행 설정:** Playwright가 API 프로세스의 API_ORIGIN을 비우던 우회를 제거하고, 웹과 API 양쪽에 테스트 주소 `http://127.0.0.1:3001`을 명시했음. 상위 셸에서 주소를 주입하지 않아도 CI와 로컬에서 같은 허용 경로를 검증하도록 했음. WEB_ORIGIN은 웹 요청 출처, API_ORIGIN은 웹 프록시의 전달 목적지라는 역할을 유지함.
- **검증:** 수정 전 단위 4개와 실제 DB 회귀 1개가 의도한 조건으로 실패했음. 수정 후 단위 159개, DB 통합 148개와 HTTP E2E 3개 통과했음. DB 없는 일반 실행은 단위 159개와 통합 파일의 일반 검사 11개를 합쳐 170개 통과했으며, 통합 148개와 중복 합산하지 않음.
  - DB 회귀는 IP 로그인 예산을 99/100으로 준비한 뒤 거부할 출처의 요청을 두 비밀번호 경로에 반복하고, 예산이 그대로인 상태에서 정상 로그인 1회가 성공하는지 확인함.
  - 설정 회귀는 development와 test에서 주소 지정 및 생략, 잘못된 경로와 인증 정보, 비HTTP 주소를 확인함. production 거부 검사도 유지함.
  - 첫 전체 통합 실행은 과거 정책인 거부 출처 차감을 기대하던 기존 검사 1개가 실패했음. 승인된 정책에 맞춰 기대값을 바꾸고, 허용 출처의 잘못된 본문과 무효 계정 연결 요청은 계속 차감하는 조건을 보존한 뒤 전체 148개 재검증했음.
  - 타입 검사, 린트, 포맷, API/Next 빌드와 DB 적용, 구조 확인 및 같은 migration 재실행 통과했음. 이번 검증의 임시 DB 컨테이너는 정리했고 기존 데이터는 변경하지 않음.
  - 검토 대응으로 무효 연결의 401과 오류 코드를 추가 확인하고 E2E 주소를 명시한 뒤, 관련 DB 통합 33개와 HTTP E2E 3개 및 정적 검사, 빌드와 DB 검사를 재실행해 통과했음. 마지막 E2E는 상위 셸의 API_ORIGIN 주입 없이 실행했음.
- **남은 위험:** DB 연결 하나와 요청 처리 중 정리가 실제 부하에서 지연을 일으키는지는 아직 측정하지 않음. 사용자가 지정한 **MVP 배포 직전**에 pool **1, 5, 10, 20** 등으로 비교할 예정임.
- **검증 범위:** 실제 Google 로그인, 메일 수신과 외부 Webhook은 이번 두 수정의 검증에 포함하지 않음. Google 신원 거부와 공백 이메일의 기존 로컬 회귀 검사는 유지함.

### Historical Docker Preview Commands

- 저장소 루트의 Windows PowerShell 기준으로 작성했음. 비밀값은 `.env.preview`에 별도 준비
  - `WEB_ORIGIN`은 `https://127.0.0.1:4443`, Google 콜백은 같은 주소의 `/api/auth/google/callback` 사용
  - `POSTGRES_PASSWORD`는 충분히 긴 난수를 영문, 숫자, 밑줄, 하이픈으로 준비. 현재 설정은 비밀번호를 DB URL에 직접 넣으므로 `@`, `:`, `/`, `#`, `%`는 사용하지 않도록 제한했음
  - 기존 DB의 비밀번호는 환경변수만 바꿔도 변경되지 않음. DB 역할의 실제 비밀번호와 설정을 함께 변경해야 함

```powershell
docker build -f Dockerfile.preview -t amuq-preview:local .
docker compose -f compose.preview.yaml --env-file .env.preview up -d --wait api worker proxy
docker compose -f compose.preview.yaml --env-file .env.preview cp proxy:/data/caddy/pki/authorities/local/root.crt docker/preview/local-ca.crt
Import-Certificate -FilePath docker/preview/local-ca.crt -CertStoreLocation Cert:\CurrentUser\Root
docker compose -f compose.preview.yaml --env-file .env.preview up -d --wait web
```

- 인증서와 이미지 준비 후 `docker compose -f compose.preview.yaml --env-file .env.preview up -d --wait`로 실행 가능. 중지는 같은 옵션 뒤에 `stop` 사용
  - `down`은 볼륨을 유지하지만 `down -v`는 DB 데이터도 삭제하므로 일반 중지, 인증서 갱신 용도로 사용하지 않도록 주의
- Node HTTPS 테스트는 공개 인증서를 `NODE_EXTRA_CA_CERTS`로 지정해야 함
- Caddy 인증서 볼륨을 잃으면 이전 인증서의 신뢰를 해제하고 새 공개 인증서를 복사, 등록한 뒤 `up -d --no-deps --force-recreate --wait web`으로 웹 재생성 필요
- preview를 더 이상 쓰지 않을 때도 해당 인증서만 신뢰 해제 가능. 아래 출력의 `Subject`, `Thumbprint`가 preview 인증서와 일치하는지 확인한 뒤 마지막 명령 실행 필요

```powershell
$previewCa = [System.Security.Cryptography.X509Certificates.X509Certificate2]::new((Resolve-Path docker/preview/local-ca.crt).Path)
$previewCaPath = "Cert:\CurrentUser\Root\$($previewCa.Thumbprint)"
Get-Item -LiteralPath $previewCaPath | Select-Object Subject, Thumbprint
Remove-Item -LiteralPath $previewCaPath
```
