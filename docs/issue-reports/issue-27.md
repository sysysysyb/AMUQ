#### Local Operation

- 전제: 저장소 루트에서 기존 Preview API가 정상 실행 중인 상태. `<preview-env-file>`은 실제 로컬 환경 파일 경로로 치환
- 환경 파일: `NGROK_URL`에 발급된 HTTPS 주소, `NGROK_AUTHTOKEN`에 토큰 저장. 토큰을 명령 인자나 로그에 출력하지 않음

```sh
docker compose -p amuq-preview -f compose.preview.yaml -f compose.preview.ngrok.yaml --env-file <preview-env-file> up -d --no-deps ngrok
docker compose -p amuq-preview -f compose.preview.yaml -f compose.preview.ngrok.yaml --env-file <preview-env-file> stop ngrok
```

- 사용 중 PC와 Docker 및 터널 실행 필요. 터널 중지 시 외부 API 연결 종료, CI는 독립 테스트 환경 유지

### Delivery Limits

- 병합 기준: 최종 게시 HEAD의 CI와 Preview READY를 재확인하고 공통 고정 별칭을 해당 배포로 갱신

- 전체 Issue CE 검토는 backend PR2 완료 후 최초 Issue 기준부터 수행 예정. PR1 병합과 27-2 착수는 각각 별도 사용자 승인 대상

#### Setup and Operation

- GitHub 설정: 사용자가 `VERCEL_TOKEN`을 Actions Secret으로 등록했고 이름 존재 확인. 프로젝트와 팀 및 고정 주소는 `VERCEL_PROJECT_ID`, `VERCEL_TEAM_ID`, `PREVIEW_ALIAS` 저장소 변수로 등록 후 값 대조. 비밀값 조회와 기록 없음
- 최초 적용: 이벤트 워크플로는 main에 있어야 실행. PR1은 기존 수동 배포 확인을 유지하고, 최초 병합 후 다음 열린 PR의 Preview에서 실제 이벤트와 토큰 권한 및 별칭 갱신 확인 필요
- 사용: 자동 갱신 성공 후 공통 고정 주소로 테스트. 별칭 갱신에는 PC 실행 불필요하며 실제 API와 인증 테스트에는 PC 및 Docker/ngrok 실행 필요
- 복구: 여러 PR 때문에 중단되거나 draft 상태로 건너뛴 경우 조건 정리 후 해당 Actions 재실행. 토큰 만료 시 같은 Secret의 값 교체 필요
- 큐 동작: [GitHub 공식 문서](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)의 최대 100개 대기 설정 사용. 도착 순서를 신뢰하지 않고 갱신 직전에 PR HEAD 재확인

<a id="backend-accepted-limits-and-delivery-checks"></a>

#### Accepted Limits and Delivery Checks

- 토큰 최소 권한: 팀 전체 권한의 VERCEL_TOKEN이 유출되면 별칭 갱신 외의 리소스에도 영향 가능. 게시 전에 Vercel이 허용하는 가장 좁은 권한인지 확인 필요. 검토자는 실제 토큰 범위를 확인하지 않았으며 비밀값을 출력하거나 기록하지 않음
- Preview 자동화: 최종 게시 HEAD의 원격 CI, 최초 실제 READY 이벤트의 repository_dispatch 실행, Vercel 토큰의 실제 실행 권한과 고정 별칭 대상을 게시 후 확인 필요. queue 키의 공식 지원 확인은 실제 자동 실행 성공을 뜻하지 않음
- 배포 경쟁: 마지막 PR 재확인과 별칭 쓰기 사이 force-push가 발생하면 잠시 이전 HEAD를 가리킬 수 있음. 새 READY 실행이 완료된 경우에만 교정 가능. 현재 HEAD 확인과 게시 후 수동 대조를 유지하며 이번 명칭 변경에서 공급자 간 원자성은 추가하지 않음
- 공급자 오류: 현재 별칭의 대상 배포가 삭제돼 404이면 수동 복구 필요. 일시적 5xx 자동 재시도는 없으며 실패 확인 후 재실행이나 후속 READY 확인 필요. 성공으로 처리하지 않는 경계는 유지
- ngrok 운영: edge에서 Preview 쿠키와 공유 비밀값을 처리하므로 운영용과 분리한 Preview 전용 값 필요. 서명된 주소 없는 직접 요청은 한도 버킷 공유. 터널 자동 재시작은 없으며 PC와 Docker 및 네트워크 유지 필요. 이전 실제 연결 검증은 [Frontend 기록](#frontend)에 보존
- 테스트 한계: repository, repositoryId, projectId, teamId와 문자열이 아닌 git.ref 거부를 각각 검증하는 사례 및 별칭 POST 실패를 직접 검증하는 사례는 미추가. 기존 41개 검사로 확인한 경계를 유지하며 보고된 재현 결함이 없어 이번 문서 수정에서 확장하지 않음
- Workflow schema 전용 검사 도구 미실행. queue 조합은 공식 문서와 원문 대조로 확인했으며 최종 실제 Actions 결과 확인은 남은 전달 조건으로 유지
- DB 이전: Claude는 migrator 내부 구현이나 실제 DB를 다시 검사하지 않았음. migration 파일 23개 원문 유지와 기존 빈 DB 및 재적용, schema와 Docker 검증을 근거로 유지
