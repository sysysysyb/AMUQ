# AMUQ Design Contract

이 문서는 승인된 AMUQ MVP 디자인을 구현 규칙으로 고정한다. 화면의 정확한 시각 값은 Figma를 따르고, 이 문서는 여러 화면에 공통으로 적용되는 동작 & 반응형 & 테마 & 상태 규칙과 구현 제외 범위를 설명한다.

## 1. 승인된 디자인 원본

- [Final Screens](https://www.figma.com/design/iArpXyXjJ3rNCDP2QfU6s8/AMUQ?node-id=1032-9888): 화면, 컴포넌트 상태, 타이포그래피, 색상, 간격과 반응형 배치의 기준
- [Prototypes](https://www.figma.com/design/iArpXyXjJ3rNCDP2QfU6s8/AMUQ?node-id=4-16): 주요 흐름, 화면 전환과 시작 지점의 기준
- 요구사항: `docs/plans/2026-09-09-0037-feat-amuq-mvp-requirements-plan.md`
- 제품 방향: `docs/STRATEGY.md`

Figma에서는 현재 `Final Screens` 페이지의 실제로 보이는 최종 프레임만 구현 대상으로 사용한다. 숨김 또는 deprecated 프레임, 오른쪽 초안, 이전 `Final Screens`와 이전 프로토타입은 참고하거나 복원하지 않는다. 화면 이름이나 문서 설명보다 렌더가 다르면 현재 보이는 최종 프레임을 우선 확인하고, 요구사항과 충돌하면 구현 전에 보고한다.

## 2. 경험 원칙

1. 사용자는 자신의 PDF가 어떤 범위와 문제로 변환되는지 확인한 뒤에만 학습을 시작한다.
2. 문제 생성, 풀이, 결과, 오답 및 북마크 재학습과 기록 확인을 하나의 순환으로 연결한다.
3. 전역 맥락과 특정 문제은행 맥락을 테마색과 헤더로 즉시 구분한다.
4. 미니 테스트와 모의고사는 여러 문제를 한 페이지에서 빠르게 푸는 방식이며, 한 문제씩 확인하는 방식은 릴레이에만 사용한다.
5. 오류, 미응답, 시간 만료, 원본 삭제처럼 되돌리기 어렵거나 불안한 순간에는 현재 상태와 다음 행동을 명시한다.

## 3. 기준 화면과 반응형

- 데스크톱 기준 뷰포트: `1440 × 900`
- 모바일 기준 뷰포트: `390 × 844`
- 두 크기는 시각 비교 기준이다. 그 사이 너비에서도 내용이 잘리거나 겹치지 않도록 유동 레이아웃을 사용한다.
- 긴 화면은 세로 스크롤을 허용한다. Figma 프레임 높이를 브라우저 고정 높이로 구현하지 않는다.
- 데스크톱의 다단 및 병렬 배치는 모바일에서 Figma 순서대로 단일 열에 쌓는다.
- 모바일에서 데스크톱 정보나 행동을 임의로 제거하지 않는다. Figma가 축약한 표현만 축약한다.
- 미니 테스트와 모의고사는 데스크톱 페이지당 10문항, 모바일 페이지당 5문항이다. 답안과 현재 위치를 저장하고 마지막 위치에서 재개한다.
- 릴레이는 모든 화면 크기에서 한 번에 한 문항을 보여준다.

## 4. 타이포그래피와 아이콘

Figma를 수정할 때 Pretendard 폰트 속성을 노드에 직접 입력하지 않고, 이미 등록된 로컬 Text Style을 적용한다. 구현에서는 같은 의미 역할을 단일 타이포그래피 토큰으로 매핑하고 화면마다 별도 값을 만들지 않는다.

| 의미 역할  | Figma Text Style          | Style ID                                     |
| ---------- | ------------------------- | -------------------------------------------- |
| Heading/03 | Pretendard SemiBold 20/28 | `S:fa88d72b5c07ce8b19acf724c29df401fa2ad16a` |
| Body/01    | Pretendard 16/24          | `S:45688afc38fe5095fefd2490f40c24d9243b8212` |
| Body/02    | Pretendard Regular 14/20  | `S:7e3ac10d571695d86c29ceb3166d5a518ab8352e` |

- 헤더 사용자 이니셜 `SY`는 `Body/01`을 사용한다.
- Google 로그인 버튼의 의도된 라벨만 Figma에 지정된 Roboto를 유지한다. 그 밖의 제품 텍스트는 Pretendard Text Style을 사용한다.
- 아이콘은 승인된 기존 아이콘과 상태 변형을 재사용한다. 텍스트 문자를 아이콘 대용으로 쓰지 않는다.
- Stepper의 완료 & 진행 중 & 진행 전 숫자는 모두 원형 Marker 내부에 둔다. 완료 숫자를 별도 오버레이로 배치하지 않는다.

## 5. 색상과 테마

색상은 Figma 변수와 의미 토큰을 사용한다. 화면에서 추출한 색을 컴포넌트마다 하드코딩하지 않는다.

| 맥락                                    | 테마 규칙                               |
| --------------------------------------- | --------------------------------------- |
| 전역 홈, 문제은행 목록과 새 문제은행 생성 | AMUQ 전역 초록색                        |
| 특정 문제은행 내부                      | 해당 문제은행에 지정된 테마색           |
| 정보처리기사 예시                       | 파란색 문제은행 테마                    |
| 문제은행 내부 학습 기록과 계정 관리       | 해당 문제은행 테마                      |
| 문제은행 목록에서 들어간 전역 계정 관리 | 학습 기록 탭 없이 AMUQ 전역 초록색      |
| 문제 풀이와 제출 후 결과                  | 해당 문제은행의 연한 테마 배경과 강조색 |

- 문제은행 테마는 사용자가 고르는 설정이 아니다. 초록색을 제외한 접근 가능한 5가지 중 서비스가 지정한다.
- 전역 홈의 반복 샘플은 서로 다른 문제은행임을 드러내도록 등록된 테마색과 시험명을 사용한다. 다섯 색을 넘으면 색 중복을 허용한다.
- 버튼, 진행률, 선택 상태, 링크와 핵심 강조는 현재 맥락의 의미 토큰을 따른다. 위험 행동은 테마색 대신 공통 위험 색을 사용한다.
- Figma 변수 컬렉션 `VariableCollectionId:2:2`의 모드를 기준으로 한다. 정보처리기사 파란 모드는 `1063:0`이다.

## 6. 헤더와 내비게이션

- 전역 홈과 문제은행 학습 홈의 왼쪽에는 `AMUQ` 로고가 있다.
- 문제은행 하위 화면에서는 같은 위치를 `← 문제은행 이름`으로 바꾸며, 선택하면 해당 문제은행 학습 홈으로 돌아간다.
- 헤더 구성, 간격, 프로필 원, 메뉴와 사용자 이니셜은 Final Screens의 최종 헤더를 재사용한다. 이전 헤더 변형을 복제하지 않는다.
- 데스크톱과 모바일 모두 브라우저 뒤로가기에만 의존하지 않고, Figma에 있는 명시적 복귀 및 취소 행동을 제공한다.

## 7. 화면과 흐름 계약

### 7.1 인증과 전역 진입

- 이메일 가입, 이메일 인증 대기, 로그인, 비밀번호 재설정과 Google 로그인을 요구사항 순서대로 제공한다.
- 일반 로그인 실패와 Google 로그인 취소/오류는 서로 다른 화면, 제목, 설명으로 구분한다.
- Google 버튼의 브랜드 표현과 Roboto 라벨은 승인된 상태를 유지한다.
- 전역 홈은 문제은행 이름, 지정 테마, 문제 수와 최근 학습일을 보여주며 `문제 생성` 진입점을 제공한다.

### 7.2 PDF 문제 생성

프로토타입의 데스크톱과 모바일 F2 흐름은 다음 순서를 고정한다.

1. Exam Info
2. PDFs
3. Analysis
4. OCR Review
5. Classification Overview
6. Editable Criteria
7. AI Generation
8. Review
9. Duplicate Compare
10. Ready
11. Finalize
12. Bank Home

- 이 순서는 요구사항 R12의 여섯 사용자 단계가 처리 상태와 검토 화면으로 세분된 것이다. 새로운 사용자 단계를 추가한 것으로 보지 않는다.
- 문서 구성의 모든 페이지는 하나의 챕터나 `생성 제외`에 속해야 한다. 미해결, 빈 범위, 겹친 범위가 있으면 생성 CTA를 비활성화한다.
- 처리 중에도 화면을 떠날 수 있고, 재진입 시 분석, 생성, 검토 필요, 일부 실패 상태와 챕터 진행 수를 복원한다.
- 일부 실패는 성공한 결과를 유지한 채 실패한 챕터만 재시도한다.
- 별도 `대량 문제 검토` 화면, 스크롤에 따라 급변하는 문항 번호 범위, 문항별 확정 버튼과 `다음 미검토 항목` 버튼은 만들지 않는다.
- 사용자는 확인 필요, 중복 가능성, 전체 문제 보기에서 필요한 문제를 수정하거나 삭제한다. 중복 비교를 마치면 `확정하기` 한 번으로 남은 전체 초안을 확정한다. 이 동작이 R23의 일괄 확정 계약이다.
- 최종 확정 전 안내와 입력은 승인된 기존 컴포넌트를 재사용한다.
- `입력 내용은 유지됩니다` 안내는 Final Screens에 배치된 상황과 위치에서만 사용하며, 임의의 폼에 확장하지 않는다.

### 7.3 미니 테스트

- 사용자는 챕터와 5, 10, 15, 20, 30문항 중 가능한 수를 선택한다. 시간 제한은 없다.
- 데스크톱은 10문항, 모바일은 5문항씩 보여준다. 한 문제씩 넘기는 UI로 바꾸지 않는다.
- 선택 답안, 미선택 상태, 페이지 위치와 진행률은 같은 세션 상태에서 계산한다.
- 진행률의 채워진 길이는 라벨의 실제 값(예: `3/20`)과 일치해야 한다. 시각적 selected/unselected 상태를 진행률 계산의 대용으로 쓰지 않는다.
- 미응답 다이얼로그는 `Mini Test / Last Page, Desktop 10 / Mobile 5` 화면을 배경으로 사용한다.
- 제출 후 점수, 정답, 해설 화면에는 풀이 화면과 같은 연한 문제은행 테마 배경을 사용한다.

### 7.4 모의고사

- 실제 시험의 문항 수와 제한시간을 사용한다. 문항이 부족하면 전부 출제하고 조정된 시간을 안내한다.
- 미니 테스트와 마찬가지로 데스크톱 10문항, 모바일 5문항씩 보여준다.
- 타이머는 화면 이탈 중에도 서버 기준으로 흐르고, 만료되면 중복 없이 한 번 자동 제출한다.
- 미응답 다이얼로그와 시간 만료 상태는 `Mock Exam / Last Page, Desktop 10 / Mobile 5` 화면을 배경으로 사용한다.
- 제출 후 결과 화면에는 풀이 화면과 같은 연한 문제은행 테마 배경을 사용한다.

### 7.5 릴레이

- 챕터, 오답, 북마크 릴레이는 세션 시작 시 대상을 확정해 섞고 한 문제씩 보여준다.
- 답을 고르고 `확인`하면 같은 화면에서 즉시 정답과 해설을 보여준다.
- 릴레이 진행 위치는 재개용으로 저장하지 않는다. 한 문제 이상 푼 세션의 풀이 수와 정답 수만 기록한다.
- 다시 시작하면 현재 대상 문제를 기준으로 새로운 순서의 세션을 만든다.

### 7.6 학습 홈, 기록과 계정 관리

- 학습 홈은 최근 모의고사 점수, 모든 학습 모드 진입점과 최근 학습 3건을 보여준다.
- 문제은행 내부 마이페이지의 학습 기록과 계정 관리 탭은 현재 문제은행 테마를 사용한다.
- 전역 문제은행 목록에서 계정 관리로 들어가면 학습 기록 탭을 표시하지 않고 전역 AMUQ 테마를 사용한다.
- 학습 기록 차트 왼쪽 축에는 점수, 아래 축에는 시험 날짜와 시간을 표시한다.
- 차트 원형 포인트는 데스크톱 hover와 키보드 focus에서 `YYYY. MM. DD HH:mm` 형식의 시험 시각 툴팁을 연다. 모바일은 tap으로 같은 정보를 열며 바깥 tap, 재tap 또는 `Esc`로 닫는다.
- 포인트의 보이는 크기는 디자인을 유지하되 상호작용 영역은 최소 `44 × 44px`이고, 포커스 링과 시험 종류, 점수, 시각을 포함한 접근 가능한 이름을 제공한다.

## 8. 공통 컴포넌트와 상태

- Button, Field, Dialog, Header, Stepper, Progress, Question Card, Answer Option, Explanation, Timer, Toast, Tabs와 Chart 표현은 Final Screens의 기존 컴포넌트와 변형을 재사용한다.
- 같은 역할의 컴포넌트를 화면별로 새로 만들지 않는다. 회원가입 비밀번호 확인 Field와 최종 확정 안내도 기존 변형을 사용한다.
- 로딩, 빈 상태, 오류, 비활성, 재시도, hover, focus, validation과 destructive 상태는 적용 가능한 화면에서 제공한다.
- 다이얼로그는 현재 작업 화면을 맥락으로 보존한 overlay다. 승인된 Last Page 배경을 다른 임의 화면으로 교체하지 않는다.
- 정답, 오답, 미응답은 색만이 아니라 텍스트와 아이콘으로도 구분한다.
- 사용자의 답안, 생성 설정이나 수정 입력을 보존하는 상태에서는 보존 여부를 명시한다. 보존을 보장할 수 없는 전환에는 같은 문구를 쓰지 않는다.

## 9. 접근성 계약

- 모든 대화형 요소는 키보드로 도달 및 실행 가능하고, 보이는 포커스 링과 목적을 설명하는 접근 가능한 이름을 가진다.
- 텍스트, 아이콘과 상태 조합은 Figma의 대비를 유지한다. 테마색 변경 시에도 동일 기준을 충족해야 한다.
- 클릭 및 탭 대상은 최소 `44 × 44px` 상호작용 영역을 확보한다. 보이는 아이콘 크기를 억지로 키울 필요는 없다.
- 오류는 관련 Field와 연결하고, 오류 요약 또는 상태 변화는 보조기술에 전달한다.
- Dialog는 열릴 때 초점을 내부로 이동하고 닫힐 때 실행 요소로 돌려보낸다. 제목 연결, focus trap과 `Esc` 닫기를 제공하되 파괴적 확정 단계에서는 오작동 방지 규칙을 따른다.
- 진행률과 Stepper는 색, 모양 외에 현재 값, 전체 값과 단계 이름을 텍스트 또는 접근성 속성으로 전달한다.
- 타이머, 자동 제출과 비동기 생성 완료는 시각 표시와 함께 과도하게 반복되지 않는 상태 알림을 제공한다.

## 10. 데이터와 UI 불변식

- 선택 답안과 진행 위치는 낙관적으로 표시하되 이동 또는 제출 전에 저장을 완료하고 오래된 응답이 새 값을 덮지 않게 한다.
- 채점과 최종 점수는 서버가 세션에 고정된 문제 revision으로 계산한다. UI는 정답을 미리 포함하거나 자체 계산을 신뢰하지 않는다.
- 미응답은 오답과 구별해 표시하지만 점수 계산에서는 오답으로 취급한다.
- 문제 수정, 삭제가 과거 점수와 기록을 다시 계산하지 않는다.
- 중복 가능성은 검토 보조 신호이며 자동 삭제나 확정 차단 조건이 아니다.
- AI 결과는 초안일 뿐이며 사용자 최종 확정 전에는 학습에 포함하지 않는다.
- 진행률, 문항 수, 답변 수와 차트 수치는 같은 서버 상태에서 파생해 서로 어긋나지 않게 한다.

## 11. 구현하지 않는 디자인

- 숨김, deprecated 프레임, 오른쪽 초안과 이전 대안
- 이전 `Classification / Desktop|Mobile`, 이전 `03 생성 설정 / Desktop|Mobile` 화면
- 별도 대량 검토 화면과 문항별 확정 흐름
- 미니 테스트와 모의고사의 한 페이지 한 문항 방식
- 문제은행 보관 및 복원, 삭제 문제 복원, 과거 테스트 문항별 상세 열람
- Final Screens에 없는 장식, 화면, 내비게이션이나 임의의 SaaS 패턴

## 12. 구현 및 검증 기준

- 구현 전에 대상 Figma 노드의 typography, fill, stroke, radius, spacing, size, alignment, constraints와 variable mode를 직접 측정한다.
- Final Screens의 공통 컴포넌트와 상태를 코드의 공통 컴포넌트로 매핑한다. 화면 복사본마다 값을 다시 작성하지 않는다.
- 프로토타입에는 64개 화면, 12개 flow starting point와 87개 연결이 검증되어 있다. 구현 흐름은 이 연결을 기준으로 하되 서버 상태에 따라 진입 조건을 확인하고 올바른 화면으로 이동시킨다.
- UI 완료 검증은 최소한 다음을 포함한다.
  - 요구사항에 지정된 focused test, type check, lint와 build
  - 핵심 흐름 Playwright E2E
  - `/ce-test-browser`
  - `/impeccable audit`
  - `1440 × 900`, `390 × 844`에서 승인된 Figma와 시각 비교
- Figma와 기술 및 접근성 요구가 충돌하면 임의로 디자인을 바꾸지 않고 차이와 대안을 보고한다.
